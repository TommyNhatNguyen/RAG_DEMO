1. Tổng quan hệ thống

Bài toán: trợ lý ảo e-learning trả lời câu hỏi của học viên dựa trên học liệu dị chất của khoá học (PDF/DOCX/PPTX, ảnh/slide, bảng, transcript audio, video bài giảng), luôn kèm căn cứ (đường dẫn tương đối + trang/slide/mốc thời gian). Đây là một hệ RAG (Retrieval-Augmented Generation) đa phương thức, single-turn (không có lịch sử hội thoại), chạy được offline trên máy Apple Silicon 16GB.

Toàn bộ hệ thống chia 3 giai đoạn độc lập, nối bằng ChromaDB:

  INGESTION                         RETRIEVAL                          GENERATION
  ─────────                         ─────────                          ──────────
  file → loader → chunk → embed     query → enhance → multi-source     hits → prompt → LLM
       → ChromaDB (2 collections)        search → fuse (RRF) → rerank       → Qwen3-1.7B (text)
       → data/index_manifest.json        → diversify → expand → compress   → hoặc Qwen3-VL-2B (ảnh trang/slide)
                                                                             → stream trả lời + trích dẫn

app/factory.py::build_services() là điểm lắp ráp duy nhất — tạo tất cả service (vector store, embedders, loaders, pipeline, retriever, generator) và trả về một AppServices dataclass. CLI (app/main.py) và HTTP API (app/api/app.py) đều gọi hàm này để lấy service, không có logic khởi tạo trùng lặp ở nơi khác.

Model 1.7B (text) và Qwen3-VL-2B (ảnh) không load khi chạy ingest/search/stats — chỉ load lười (lazy) khi thực sự gọi ask lần đầu. Điều này quan trọng để hiểu log "im lặng" lúc chạy CLI: không phải treo máy, mà model chưa cần load.

6. Ingestion pipeline

Điều phối bởi app/pipeline/ingestion.py::IngestionPipeline. ingest(path) gọi iter_input_files() (đệ quy nếu path là folder, bỏ qua .DS_Store/file ẩn), rồi với mỗi file gọi ingest_file():

ingest_file(path)
 ├─ document_id = sha256(bytes file)           (app/ids.py::file_sha256)
 ├─ nếu hash đã thấy trong lần chạy này → skip (chống trùng khi 1 lệnh ingest quét nhiều path)
 ├─ kind = detect_kind(path)  # document|text|image|video, theo suffix
 ├─ so hash mới với hash cũ theo relative_path trong manifest:
 │    • path cũ có hash khác → _delete_document() (xoá vector + toàn bộ file sinh ra) rồi tiến hành index lại
 │    • video: is_video_complete() kiểm tra processed_duration + video_pipeline_version → mới quyết định skip
 │    • non-video: _should_rechunk() so `chunk_profile()` hiện tại với cái lưu trong manifest, hoặc `--rechunk`
 ├─ _process(path, id, kind) → loader tương ứng → chunk (nếu cần) → IndexingService
 └─ manifest.record(...) ghi lại content_types + chunk_profile/video stats

Sau khi ingest xong toàn bộ file, _maybe_rebuild_bm25() tự rebuild data/bm25.pkl nếu có gì thay đổi (hoặc file BM25 chưa tồn tại) — không cần chạy lệnh riêng, trừ khi bạn chỉ muốn rebuild BM25 mà không ingest gì (rebuild-bm25, §12).

6.1 Document — PDF/DOCX/PPTX/PPT (app/loaders/docling_loader.py)

  • Hỗ trợ .ppt (mới, 2026-09-30): Docling không đọc được định dạng PowerPoint nhị phân cũ (.ppt), chỉ đọc .pptx (XML/OOXML). DOC_EXTS (app/loaders/base.py) nay gồm cả .ppt; khi gặp .ppt, docling_loader.py gọi app/processors/office_convert.py::convert_ppt_to_pptx() để chuyển đổi tạm bằng LibreOffice headless (yêu cầu soffice cài sẵn trên máy, tự dò qua find_soffice()) rồi parse bản .pptx tạm đó; DocumentAsset.relative_path/file_type lưu trong Chroma vẫn giữ nguyên đường dẫn/định dạng .ppt gốc, không phải file tạm đã convert.
  • Dùng docling.DocumentConverter với PdfPipelineOptions(do_ocr=False, do_table_structure=True, generate_picture_images=True, generate_page_images=True) — Docling tự OCR tắt, hệ thống tự quyết định OCR bằng Tesseract khi cần (không phải Docling OCR).
  • Text blocks: đi qua doc.iterate_items(), heading/title → cập nhật section hiện tại; bỏ page header/footer/footnote/picture/table label.
  • Tables → table.export_to_markdown(doc) → lưu là 1 "text-like" record content_type=table trong text_embeddings (không embed ảnh bảng riêng).
  • Pictures (ảnh nhúng) → PNG dưới storage/images/{doc_id}/picture_NNN.png.
  • Page images — luôn giữ cho PDF/PPTX (mọi trang); với DOCX chỉ giữ khi native text < 40 ký tự (MIN_NATIVE_TEXT). Lý do: PDF/PPTX cần ảnh trang để retrieval thị giác + Qwen-VL đọc trực tiếp; DOCX phần lớn có text sạch nên tiết kiệm.
  • OCR fallback: nếu không trang nào có ≥40 ký tự native mà vẫn có page image → chạy Tesseract trên từng page image, text OCR được thêm vào cả text_blocks (để chunk & search) và ImageAsset.ocr_text.

6.2 Text/Markdown & Image

TextLoader (txt/md): heading ATX (#..######) tách section boundary, không có khái niệm page. ImageLoader (ảnh đơn): chuẩn hoá RGB (to_rgb, xử lý alpha/paste nền trắng), lưu original.png, chạy OCR — nếu có text OCR thì cũng đẩy vào text_blocks để có bản text-embedding song song với visual-embedding.

6.3 Video — pipeline 7 bước (app/loaders/video_loader.py)

[1/7] probe_video (ffprobe)         duration/width/height/fps/has_audio
        └─ VIDEO_MAX_DURATION cắt "processed" duration cho smoke test (WARNING log, không cắt file thật)
[2/7] extract_audio (ffmpeg)        → storage/audio/{id}.wav (16kHz mono PCM), reuse nếu checkpoint đã qua "audio"

                                     nếu không có → faster-whisper (WhisperModel, compute_type=int8, CPU-only)
[4/7] sample_coarse_frames (ffmpeg) 1 frame mỗi VIDEO_COARSE_SAMPLE_INTERVAL=10s, JPEG rẻ, không decode cả video vào RAM
[5/7] SemanticFrameSelectionStrategy  với mỗi cửa sổ VIDEO_SEGMENT_DURATION=30s:
        • pHash near-duplicate filter (VIDEO_FRAME_SIMILARITY_THRESHOLD=0.90)
        • score = 0.35·visual_change + 0.30·ocr_change + 0.20·scene_boundary + 0.15·temporal_coverage
        • giữ tối đa VIDEO_MAX_REPRESENTATIVE_FRAMES=3 frame/cửa sổ
[6/7] embed transcript windows (text_embedder)   → text_embeddings, content_type=video_segment
[7/7] embed selected frames (vl_embedder)         → visual_embeddings, content_type=video_frame

Checkpoint & resume (app/processors/video_checkpoint.py): VideoCheckpoint ghi storage/videos/{id}/checkpoint.json với stage ∈ {metadata, audio, transcript, coarse_frames, selected, indexed} và video_pipeline_version="v2-long". Nếu tiến trình bị crash giữa đường, lần chạy lại tái sử dụng WAV/transcript đã có (miễn processed_duration khớp trong dung sai DURATION_TOLERANCE=1.0s) — không transcribe lại từ đầu. IndexManifest.is_video_complete() quyết định video đã hoàn chỉnh (đủ duration + đúng pipeline version) hay cần index lại.

Cửa sổ transcript được gán theo assign_pieces_to_windows() (app/chunking/video_chunker.py) — mỗi câu Whisper thuộc về cửa sổ chứa thời điểm bắt đầu của nó, không cắt giữa câu.

Tuỳ chọn hiếm gặp: nếu bạn từng dùng công cụ Whisper MLX riêng để transcribe trước (ví dụ trên máy khác nhanh hơn), đặt kết quả cạnh video theo tên <video_stem>_segments.json — hệ thống tự phát hiện và bỏ qua bước transcribe (VideoLoader._find_timestamp_sidecar).

8.1 Fetch/where/prefix logic

  • --source: nếu là tên file/path có suffix hợp lệ → Chroma where={relative_path|filename: ...} chính xác (source_clause). Nếu là folder (không có suffix) → không dùng Chroma where mà lọc bằng matches_prefix() sau khi fetch (vì Chroma không hỗ trợ "starts with" tự nhiên) — khi đó dense_n được nhân 5 để có đủ candidate sau lọc.
  • --course: theo mặc định không đẩy vào Chroma where (để tương thích vector cũ thiếu field course) — chỉ post-filter bằng matches_course(). Chỉ khi settings.course_prefilter=true (dùng trong benchmark, §11) thì mới filter cứng ở Chroma.
  • content_type: luôn post-filter, không đẩy vào Chroma where trong code hiện tại của retriever (mặc dù chroma_where() có hỗ trợ) — kiểm tra kỹ nếu bạn định dựa vào Chroma-side filter cho content_type.

8.3 Expand & Compress — "parent/child" và "contextual compression" không cần model mới

app/retrieval/expand.py::expand_hits(): với hit content_type ∈ {text, table} có page_number → ghép toàn bộ chunk cùng document_id+page_number (join theo chunk_index tăng dần) làm "parent" context. Với video_segment (và text/table không có page) → ghép chunk_index-1, chunk_index, chunk_index+1 (sentence-window kiểu neighbor). Không tạo embedding mới, chỉ query Chroma get(where=...) thêm.

app/retrieval/compress.py::compress_hits(): nếu nội dung hit <240 ký tự thì giữ nguyên; dài hơn thì tách câu (regex trên . ! ? … \n) và chỉ giữ câu có token trùng với query gốc + các sub-query — hoàn toàn extractive, không gọi LLM thứ hai (đây là quyết định thiết kế rõ ràng trong docs/rag-production-checklist-handoff.md: không dùng LLMChainExtractor).

9.1 Vì sao "thinking" luôn tắt

GenerationService._ensure_loaded() patch tokenizer.apply_chat_template để luôn ép enable_thinking=False khi gọi, bất kể caller truyền gì — đây là cách duy nhất kiểm soát hành vi "suy nghĩ" của Qwen3 vì tham số này nằm trong template, không phải trong generation_config. README nhấn mạnh: nếu bật LLM_ENABLE_THINKING=true hoặc bỏ patch này, câu trả lời có thể trống hoặc chỉ chứa block <think> — ThinkStreamFilter là lưới an toàn thứ hai khi stream token.

9.2 Quản lý RAM giữa model text ↔ VL

Hai model KHÔNG cùng ở RAM một lúc theo thiết kế: _ensure_vl_loaded() gọi _release_text_model() trước khi load Qwen-VL; ngược lại mọi lời gọi _invoke()/_stream() (text) gọi _release_vl_model() trước. Cả hai release đều gc.collect() + torch.mps.empty_cache() nếu có MPS. Đây là lý do câu hỏi hỏi cả PDF ảnh và tiếp một câu text sẽ có độ trễ tải lại model — chấp nhận được trên máy 16GB, nhưng là điểm cần biết nếu bạn định thêm caching đa model.

9.3 Prompt & chống bịa (app/generation/prompts.py)

SYSTEM_PROMPT tiếng Việt, yêu cầu: course-aware, multimodal, evidence-grounded, không bịa chương/lộ trình/URL, trích dẫn chỉ gồm đường dẫn tương đối + trang/mốc thời gian (không markdown link, không http://, không "#chunk"). _FALLBACK_ANSWER (service.py) là câu trả lời "không đủ căn cứ" cứng khi cosine thấp — không đưa câu hỏi tới LLM trong trường hợp này, tránh LLM tự bịa khi ngữ cảnh rác.

11. Evaluation framework (app/eval/)

Có 2 hệ eval tách biệt, đừng nhầm hai concept này:

A. Golden-set eval (nhanh, dùng hằng ngày)

evals/golden.jsonl → CLI eval → app/eval/runner.py::run_eval():

  • Với mỗi item: retrieve (+generate nếu không --retrieve-only)
  • path_recall_at_k/path_precision_at_k (metrics.py) so expected_paths với path thực nhận được
  • Nếu không --retrieve-only: chấm faithfulness/answer_relevancy/context_precision/context_recall bằng RAGAs (nếu extra eval cài) hoặc fallback: chính Qwen3-1.7B tự chấm JSON (judge.py)
  • build_report() tính weakest_metric + next_step theo HANDOFF_MAPPING (bảng ánh xạ metric yếu → hướng sửa, xem §14) + warning nếu faithfulness <0.85 (chỉ warning, không fail CI)

B. Retrieval benchmark leakage-free (nghiên cứu/luận văn)

app/eval/retrieval_benchmark.py — dùng cho so sánh hệ thống nghiêm ngặt (baseline vs proposed), tách biệt hoàn toàn ground-truth khỏi input retrieval:

  1. prepare-retrieval-queries <questions_draft*.json> → chỉ giữ question_id/question/course_id vào benchmark_queries.jsonl (loader từ chối nếu có field khác — chống leakage cứng)
  2. benchmark-retrieve --profile baseline|proposed [--rerank] [--use-generation-pipeline] → chạy retriever thật, lưu Top-K resumable (--resume) vào results/*.jsonl; cờ mới --use-generation-pipeline (thêm 2026-09-30) gọi GenerationService.retrieve_for_eval() thay vì retriever.search() trực tiếp, để benchmark đi qua đúng luồng enhance/HyDE/reflect-loop mà ask dùng
  3. score-retrieval <questions> <results> [--resource-id-aliases evals/resource_id_aliases.json] — đọc lại bộ câu hỏi gốc để đối chiếu evidence (resource_id + page/slide/timestamp-range match), tính Precision/Recall/F1 @1/5/10, có xử lý answerable=null, loại câu có ground-truth resource chưa được index (corpus_coverage), và (mới) chuẩn hoá mã tài nguyên lệch chính tả/định dạng qua một bảng ánh xạ tĩnh trước khi so khớp — nạp mặc định nếu tệp tồn tại, tắt bằng --no-resource-id-aliases

Dòng cầu nối giữa hai hệ A/B (mới, 2026-09-30): prepare-golden-from-draft <questions_draft*.json> --out evals/golden_v7.jsonl (app/eval/question_draft_bridge.py) chuyển bộ câu hỏi dạng A (category/difficulty/evidence) sang schema golden.jsonl của hệ B, để chạy được eval (đánh giá sinh câu trả lời) trên cùng bộ câu hỏi dùng cho retrieval benchmark. app/eval/runner.py tự phát hiện khi mọi trace có ground_truth rỗng và chuyển sang chấm bằng judge.py::score_reference_free() (chỉ faithfulness/answer relevancy, bỏ qua context precision/recall vì không có câu trả lời mẫu để so), đồng thời tính thêm citation precision/recall bằng cách so last_hits thật sự được đưa vào ngữ cảnh với evidence (dùng lại đúng hàm metrics_at_k/alias ở trên). CLI eval giờ có thêm --rerank (mặc định tắt, trước đây luôn ép tắt không điều kiện).

evals/reports/dashboard.html (app/eval/dashboard.py::render_dashboard) tổng hợp assets-inventory + vector-inventory + eval scores thành 1 trang HTML tĩnh, sinh bằng CLI report.

Kết quả benchmark v7 hiện tại (chạy 2026-09-30/10-01, bộ câu hỏi questions_draft_v7.json 400 câu, corpus coverage 100% sau khi đóng gap .ppt + sửa mã tài nguyên lệch chính tả — xem §16, §17 và EXPERIMENT_LOG.md mục 16 để biết đầy đủ):

  • Khi bật rerank với bug chat-template chưa sửa (§8.2), kết quả tệ hơn baseline ở mọi chỉ số.
  • Khi bật rerank đã sửa đúng mẫu hội thoại, hệ hybrid vượt baseline với khoảng tin cậy bootstrap 95% không chứa 0 ở phần lớn chỉ số tại K=5/K=10 (F1@10: 0,0916→0,1121; recall@10: 0,3515→0,4671) — bằng chứng thống kê tích cực đầu tiên trong dự án.

14. Cách đánh giá chất lượng khi bạn thay đổi pipeline

  1. Chạy baseline: python -m app.main eval evals/golden.jsonl --text-only --retrieve-only --out evals/reports/baseline.json (nhanh, không load LLM).
  2. Đổi 1 thứ (chunk size, fetch_k, bật rerank...), rebuild BM25 nếu cần (rebuild-bm25), chạy lại, so weakest_metric.
  3. Theo bảng ánh xạ HANDOFF_MAPPING (app/eval/metrics.py) để chọn hướng sửa:
Metric yếu nhấtHướng sửa gợi ý
context_precision / path_precisionChunking (CHUNK_SIZE_*) hoặc metadata filter (--source/--course/--content-type)
faithfulnessSửa prompt hoặc CONTEXT_COMPRESS (đừng nhồi ngữ cảnh dư)
context_recall / path_recallHybrid/RETRIEVER_FETCH_K; chỉ khi vẫn yếu mới bật QUERY_HYDE=true hoặc MAX_RETRIEVE_LOOPS=1
answer_relevancyQuery enhance / prompt generation

Không bật HyDE/reflect-loop mặc định — cả hai đều off theo thiết kế (đắt tài nguyên trên 16GB) và chỉ nên bật có chủ đích khi metric recall cụ thể yếu, có đo trước/sau.

Với thay đổi lớn hoặc câu hỏi "hệ mới có thật sự tốt hơn không" cho mục đích báo cáo/luận văn — dùng benchmark leakage-free ở §11.B với bộ câu hỏi questions_draft_v7.json (400 câu, có category/difficulty, corpus coverage 100%), không dùng golden-set 35 câu pilot ban đầu (quá nhỏ để kết luận thống kê). Luôn kèm kiểm định bootstrap ghép cặp (document/KLTN_MM-RAG/tools/retrieval_stats_v7.py là ví dụ tái dùng được) — tự thấy "hệ mới cao hơn" trên bảng số không đủ để kết luận nếu khoảng tin cậy còn chứa 0.
